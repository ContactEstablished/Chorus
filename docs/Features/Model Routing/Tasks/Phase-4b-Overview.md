## Phase contract

Make a routing tier change what an OpenCode **Team helper** sends. In the Team dialog, every helper slot that routing can serve — OpenCode on an OpenRouter API-key credential that `routing:credentials` lists, with a registry model in its base or `:nitro` form — gets a tier dropdown: Budget, Balanced, Fast, Nitro or "OpenRouter default". Per MR-D15 a slot on the `:nitro` model starts on Nitro and any other slot on OpenRouter default. The renderer sends only the tier's name, as an optional `routingTier` on that Team member (4a K2's rule). Main refuses a tier it cannot serve when the team launches, with a stated reason. Before **every** helper attempt, main resolves the tier itself on the `helper` profile for that member's own credential and effort (MR-D32): a ranked tier on numbers older than 60 minutes refuses that attempt before any decrypt or spawn, and Nitro always resolves. Main records the exact selection on the attempt and carries the provider object (or Nitro's `data_collection: deny`) per process in the helper's `OPENCODE_CONFIG_CONTENT`, merged into the model entry the helper already declares, so its measured options (the `:nitro` low variant, the 64k cap, `--agent build`) are kept. A routed attempt that fails with OpenCode's generic provider error names its tier and suggests a refresh or another tier; Chorus never switches a tier on its own. The Settings preview note changes, because Team helpers now use tiers.

**Prime constraints.** Zero cost throughout: no paid run, no Refresh pressed by any test, harness or drive, no OpenCode request beyond the loopback stand-in, and no real lead or helper CLI started by any check. No interactive re-rank: "Re-rank and relaunch" is Phase 5 (MR-D33). No launch-profile tiers (MR-D27). No automatic key-bearing guardrail revalidation: Phase 4b adds no key-bearing call at all (MR-D18/D214 unchanged; `resolveLaunch` never decrypts). MR-D17 stays open. No remembered tier for helpers.

The [feature roadmap](../roadmap.md) is authoritative for MR-D1 to MR-D33 and gates MR-G1 to MR-G8. Where [Plan_1](../Plan_1.md) §12 ("Runtime failover", "Re-rank now") differs from this document, this document wins: helpers have only a generic error signal and no mid-run swap. Phase 4a's contracts are in the [Phase 4a overview](Phase-4a-Overview.md).

**Exit:** MR-G1 to MR-G6 and MR-G8 pass through zero-cost checks: `verify-routing-body.mjs` `PASS (18 checks)` with the helper half built by Chorus's real helper builder against the real OpenCode 1.18.34 at a loopback stand-in; the new main-process Team harness `verify-routing-team.mjs` `PASS (16 checks)`; the new built-app Team dialog drive `verify-routing-team-ui.mjs` `PASS (15 checks)` with 2 PNGs; the Settings drive `PASS (16 checks)` with the new note; the Team regression verifier `verify-team-storage.mjs` (repaired for v28 in 0.9.2, `efabe9b`) still reporting `"passed": true`; and, unchanged, the ranker `PASS (30 checks)`, the IPC drive `PASS (20 checks)`, the UI harness `PASS (20 checks)` and the launch drive `PASS (20 checks)`.

## Risks

- **A refused attempt is consumed.** A stale, empty or unavailable refusal uses one of the task's three attempts (Q1). A long run without background observation loses an attempt each time a ranked helper starts after the snapshot passes 60 minutes.
- **Long runs need observation.** Observation is dormant until a credential is designated (MR-D19); it refreshes the model's snapshot, but a credential's account file is written only by a refresh with that credential, so a helper whose credential was never refreshed ranks with `accountEligibility: 'unknown'` (as in 4a).
- **OpenCode allow-lists against updates.** Chorus-launched OpenCode no longer updates itself (MR-D31), but an OpenCode the user starts elsewhere can still upgrade the shared binary; helpers are then refused until the version is re-measured, and the body script refuses an unmeasured version.
- **Lead versions move under the gates.**
  - 0.9.2 admitted Claude Code 2.1.289 and Codex 0.160.0 as leads on static, zero-cost evidence (user decision). Earlier lead admissions used real subscription runs.
  - Chorus-launched Claude and Codex no longer update themselves, and the user turned Claude Code's self-update off machine-wide.
  - A deliberate update still disables Team leads until the new version is re-admitted.
- **Downgrade.** Runs, attempts and presets written by 4b cannot be read by 0.9.2 or earlier (Q5).
- **The lead sees and can act on tiers.** `team_roster` exposes `routingTier`, and the failure note invites a revision to a helper on another tier. That is the lead's decision within the roster the user configured, never Chorus switching on its own.
- **`TeamService` has no unit tests.** Every wiring proof is the Electron-hosted harness (T1–T16); review must check the call order against ImplementationSpec-4b-2.
- **The dialog and the attempt can disagree.** Time passes between the dialog's ranking and each attempt's resolution, time-of-day prices can change an order, and the attempt's resolution wins.
- **The relaunch attribution-key gap** (C22) stays open; out of scope.
- **The provider error is generic.** OpenCode's own error text is discarded (`parser.ts:108`), so a routed failure note cannot say which provider failed or why (Q4).
- **The UI drive depends on a composed PATH.** A real executable anywhere on the app's PATH beats a stub `.cmd`, and the app probes more than the two stubbed CLIs (`capabilities()` probes Codex; opening the launch dialog detects all five agents). The drive must strip every directory holding a `claude`, `codex`, `kimi`, `opencode` or `grok` executable or shim, and refuse to run unless `where.exe` finds only the stubs for `claude` and `opencode`, nothing for the other three, and still finds `node` and `git` (C19).
- **The harness spawns `where.exe`.** The real helper builder resolves `opencode` on PATH before it builds, as every helper launch does; the harness asserts the resolution and never runs the resolved executable. It needs an `opencode` on PATH that `resolveCli` can resolve (true on this machine: the npm shim).
- **The Team verifier leaves its evidence.** `verify-team-storage.mjs` writes `%TEMP%\chorus-team-storage-*` and never deletes it (pre-existing behaviour).
- **CRLF and mixed files.** Sixteen CRLF files, one LF file (`helpers/types.ts`) and one mixed file (`helpers/common.ts`) are edited; `common.ts` and `TeamLaunchDialog.vue` are edited byte-wise only; the `Edit` tool can rewrite a CRLF file as LF. Check `git diff --stat`, `git ls-files --eol` and the byte counts the specifications give after every edit.
